# HealSmartAI — Full-Stack Healthcare Information Portal (Demo)

> **Important Disclaimers & Scope Notice**
> - **Rule-Based Engine (NOT OpenAI / LLM):** Symptom evaluations are generated by a deterministic, local keyword-matching rule engine — **not** by OpenAI or any artificial intelligence language model.
> - **No Cloud / Firebase Dependencies:** Persistence is handled 100% locally via SQLite (`better-sqlite3`). Firebase and paid external APIs are **not** used.
> - **No Authentication / Authorization Implemented:** User login, authentication, and role-based access control (RBAC) are **not** currently implemented. The API binds to `127.0.0.1` for local development only — **do not deploy patient-record endpoints publicly**.
> - **Non-Diagnostic & Fictional Data Only:** This application is strictly for local software engineering demonstration and general health education. It is **not** a medical diagnostic tool, cannot reliably triage medical emergencies, and must only be used with **fictional demo patient records** (never real personal or protected health information / PHI).

---

## 1. Project Overview

**HealSmartAI** is a full-stack healthcare information and fictional patient-record management web application built with **React + Vite**, **Node.js + Express**, and **SQLite**.

It demonstrates clean REST API design, parameterized SQL persistence, Joi schema validation, centralized error handling, a deterministic symptom-information engine with conservative emergency red-flag warnings, and a responsive light-glassmorphism UI.

## 3. Features Implemented & Tested

1. **Deterministic Symptom Information Checker (`/symptoms`)**
   - Multi-symptom input (quick-add chips + custom keyword entry).
   - Severity (`mild`, `moderate`, `severe`), optional duration, and optional link to a fictional demo patient.
   - Rule-based output displaying matched categories, educational health overview, self-care tips, when to seek medical care, and explicit non-AI / non-diagnostic disclaimers.
   - Conservative emergency safety banner when red-flag keywords (e.g., chest pain, shortness of breath, stroke symptoms, fainting) are detected.
   - Paginated symptom-check history persisted in SQLite.
2. **Fictional Patient Records CRUD (`/patients` & `/patients/:id`)**
   - Paginated directory with search across first name, last name, email, and phone.
   - Create, edit, and delete (with confirmation modal) fictional patient profiles.
   - Detailed patient view showing demographics, linked symptom check history, and fictional clinician notes timeline.
   - Inline client-side and backend Joi validation error feedback.
3. **Doctor Dashboard Demo (`/dashboard`)**
   - Live SQLite aggregate KPI cards: Total Demo Patients, Total Symptom Checks, Fictional Doctor Notes, and Emergency Warning Checks.
   - Severity distribution progress breakdown (`mild`, `moderate`, `severe`).
   - Recent symptom-check activity table with severity filter and pagination.
   - Recent fictional clinician notes feed.
4. **System Health & Proxy Verification (`/`)**
   - Landing page with live backend status, SQLite engine version, and query latency via `GET /api/health`.

## 8. API Endpoint Documentation

All responses return a uniform JSON envelope:
- Success: `{ "success": true, "meta": { ... }, "data": { ... } }`
- Error: `{ "success": false, "error": { "message": "...", "details": [ ... ] } }`

| Method | Endpoint | Description | Status Codes |
|---|---|---|---|
| `GET` | `/api/health` | Returns API uptime, environment, SQLite version, and query latency. | `200` |
| `GET` | `/api/patients` | Paginated list of demo patients (`?page=1&limit=10&search=...`). | `200`, `400` |
| `POST` | `/api/patients` | Create a fictional demo patient (`first_name`, `last_name`, `date_of_birth`, `gender`, etc.). | `201`, `400` |
| `GET` | `/api/patients/:id` | Retrieve a single demo patient by ID. | `200`, `400`, `404` |
| `PUT` | `/api/patients/:id` | Update an existing demo patient by ID. | `200`, `400`, `404` |
| `DELETE` | `/api/patients/:id` | Delete a demo patient by ID (cascades notes, sets symptom check `patient_id` to `NULL`). | `200`, `400`, `404` |
| `POST` | `/api/symptoms/check` | Evaluate `symptoms` array (`duration`, `severity`, optional `patient_id`) and save check. | `201`, `400`, `404` |
| `GET` | `/api/symptoms/history` | Paginated symptom-check history (`?page=1&limit=10&patient_id=...`). | `200`, `400`, `404` |
| `GET` | `/api/dashboard/stats` | Live SQLite aggregate counts (patients, checks, notes, emergency warnings, severity breakdown). | `200` |
| `GET` | `/api/dashboard/recent` | Paginated recent symptom checks (`?page=1&limit=10&severity=...`). | `200`, `400` |
| `GET` | `/api/notes` | Paginated fictional doctor notes (`?page=1&limit=10&patient_id=...&note_type=...`). | `200`, `400`, `404` |
| `POST` | `/api/notes` | Add a fictional doctor note (`patient_id`, `author`, `note_type`, `content`). | `201`, `400`, `404` |

## 9. How the Rule-Based Symptom Information Engine Works

Located in `backend/src/routes/symptoms.js`, the symptom engine is **100% deterministic and rule-based**:

1. **Input Normalization:** Incoming symptom strings are trimmed and lowercased.
2. **Emergency Red-Flag Scan (`EMERGENCY_TRIGGERS`):** Checks input against conservative emergency keyword patterns:
   - Chest Pain / Cardiac Warning Signs (`chest pain`, `chest pressure`, `heart attack`, etc.)
   - Severe Breathing Difficulty (`shortness of breath`, `difficulty breathing`, `gasping`, etc.)
   - Stroke-Like Neurological Symptoms (`slurred speech`, `facial droop`, `arm weakness`, etc.)
   - Loss of Consciousness (`fainted`, `unconscious`, `seizure`, etc.)
   - Severe Bleeding or Trauma (`coughing up blood`, `vomiting blood`, `anaphylaxis`, etc.)
   - If matched, `emergency_safety.is_emergency_warning` is set to `true` with a prominent safety notice instructing the user that the rule engine cannot triage emergencies and to contact emergency services (`911`) immediately.
3. **Symptom Category Matching (`SYMPTOM_RULES`):** Matches input against 7 curated educational modules:
   - `fever` (Fever & Elevated Body Temperature)
   - `headache` (Headache & Head Discomfort)
   - `cough` (Cough & Upper Airway Irritation)
   - `sore_throat` (Sore Throat & Pharyngeal Discomfort)
   - `fatigue` (Fatigue & Low Energy)
   - `nausea` (Nausea & Upper Digestive Upset)
   - `stomach_discomfort` (Stomach Discomfort & Gastrointestinal Symptoms)
4. **Unclassified Fallback:** If no specific category matches, the engine returns a conservative `general_unclassified` educational response with general monitoring and clinician consultation advice.
5. **SQLite Persistence:** Every evaluation is stored in `symptom_checks` along with the medical disclaimer and optional `patient_id`.

## 10. Sample Fictional Demo Workflow

1. Open `http://localhost:5173/patients` and click **Add Demo Patient**.
2. Enter fictional details (e.g., `Elena Vance`, DOB `1988-04-15`, Gender `Female`, Blood Type `O+`) and click **Create Demo Patient**.
3. Go to **Symptom Checker** (`/symptoms`), click the quick-add chips for `Fever` and `Headache`, select `Moderate` severity, choose `Elena Vance` from the demo patient dropdown, and click **Check Symptoms**.
4. Review the rule-based educational output, self-care tips, and non-diagnostic disclaimer.
5. Click on `Elena Vance` in the Recent Symptom Check History table (or navigate to `/patients`) to open her **Patient Detail Page**.
6. Under **Fictional Clinician Notes**, add a follow-up note (e.g., author `Dr. Demo`, content `Advised rest and hydration for fictional demo walkthrough`) and click **Add Fictional Note**.
7. Navigate to **Doctor Dashboard** (`/dashboard`) to verify live SQLite KPI counters, severity distribution bars, and activity feeds reflect your new records.

## 12. Known Limitations & Future Improvements

- **No Authentication or RBAC:** All endpoints are currently unauthenticated for local demonstration simplicity. Adding JWT/session authentication and clinician vs. patient role-based access control is the primary next step before any network deployment.
- **Keyword-Based Matching:** The deterministic symptom engine relies on substring keyword matching rather than clinical NLP or ontology mapping (such as SNOMED-CT / ICD-10).
- **Single-Node SQLite Storage:** `better-sqlite3` is ideal for local development and single-instance deployments, but high-concurrency multi-node environments would require migrating to PostgreSQL.
- **No Automated Unit Test Runner in `package.json`:** End-to-end API and Playwright browser verification scripts were executed during build verification; adding a dedicated `vitest` or `node --test` script in `package.json` is a recommended enhancement.
